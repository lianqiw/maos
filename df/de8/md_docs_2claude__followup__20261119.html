Follow-up fixes to the first bug-fix commit, 2026-11-19

Commit: "Fix follow-up issues in the bug-fix commit" (base e6403afd3). These are review findings in the code changed by e6403afd3.

sys/daemonize.c: lock_file_version

  • The retry loop when the lock holder's PID was stale (kill(pid,0) failed) or not yet written (file empty) could loop forever. It now retries at most 10 times, one second apart, then returns -1 ("held by an unknown process").
  • kill(pid,0) failing with EPERM (process exists, other user) was treated as "exited". Only ESRCH now means the holder is gone.
  • If fdopen(dup(fd)) failed, the function returned the fd although it did not hold the lock. It now fails.
  • lseek(fd,0,SEEK_SET) before re-reading the PID: the dup'd FILE shares the file offset, so a retry read from the end of the file and found no PID.

tools/scheduler_http.c

  • The web password file (htpasswd) and session cookie file (htcookie) were created with fopen(fn,"w"), i.e. world readable under the default umask. They are now created by fopen_private() with O_CREAT|O_EXCL and mode 0600.
  • If generate_session_cookie() returned NULL, fprintf(fp,"s\n",NULL) was called. The line is now written only when non-NULL.

Doc block placement

  • maos/powfs.c setup_powfs_llt and maos/plot_utils.c powfs_legend: the return type had been separated from the function name by a doc comment inserted in between. Rejoined the declaration and removed the stale comment.
